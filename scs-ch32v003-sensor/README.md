# CH32V003: датчик изменения ёмкости

Сенсор обнаруживает поток воды по изменению ёмкости металлической пластины, закреплённой снаружи трубы аэрлифта. Вода в такой трубе движется порциями, между которыми проходят воздушные промежутки. Когда они сменяют друг друга рядом с пластиной, её ёмкость немного меняется.

Сенсор многократно заряжает и разряжает пластину через резистор. Таймер измеряет время, за которое напряжение при разряде достигает порога переключения входа микроконтроллера. Изменение ёмкости влияет на это время, поэтому по его колебаниям можно судить об изменениях рядом с пластиной.

Изменения очень малы, и по одному измерению их трудно различить. Поэтому сенсор складывает результаты нескольких измерений в группы, а затем оценивает, насколько суммы колеблются за период наблюдения. Повторные измерения позволяют заметить изменчивость, которая слабо видна в отдельных отсчётах.

Абсолютную ёмкость сенсор не определяет и не использует как признак потока. При пустой трубе или неподвижной воде показания могут быть относительно стабильны, хотя сама ёмкость в этих случаях различается. Проходящие порции воды вызывают колебания, и именно их оценивает сенсор.

Сенсор выдаёт числовой показатель изменчивости `D`. Управляющий контроллер запрашивает накопленные результаты и пересылает их в компьютер для хранения и анализа. Движение датчика, вибрация и электрические помехи тоже могут вызывать колебания, поэтому пороги и правила обнаружения потока нужно проверять в условиях установки. Сам показатель не доказывает периодичность потока.

## Прошивка и алгоритм

Прошивка рассчитана на **CH32V003J4M6 (SOP8)**. Использует прямые обращения к регистрам, собственный код запуска и скрипт линкера. SDK и libc для сборки не нужны.

Алгоритм:

1. Разрядить измерительную цепь и перевести B во вход.
2. Аппаратно переключить A через TIM2_CH3 и захватить TIM2_CH1 время достижения цифрового порога B при заряде.
3. Выдержать зарядную паузу, переключить A в ноль и захватить время спада B при разряде через R.
4. Принудительно разрядить цепь через GPIO B. Повторить измерение `SAMPLES` раз, накопив сумму захватов разряда. Результат захвата заряда не используется в статистике.
5. Накопить окно из 128 сумм, отсортировать его и вычислить среднее абсолютное отклонение от медианы.
6. Поместить результат в кольцевой буфер и начать новое, неперекрывающееся окно. Передавать готовые результаты только по запросу PC4.

По умолчанию `SAMPLES=16`: окно содержит 2048 измерений. Между блоками процессор входит в Standby. После последнего блока окна сначала завершается расчёт, а при наличии запроса завершается и передача UART.

## Подключение

```text
PD6 (A / TIM2_CH3) -- R --+-- PC1 (B / TIM2_CH1)
                          |
                          C
                          |
                         GND
```

Включён полный remap TIM2 (`TIM2_RM=11`): CH1=PC1, CH3=PD6.

### Распиновка CH32V003J4M6 (SOP8)

Ножки пронумерованы по даташиту. Указаны функции, относящиеся к проекту, а не все альтернативные функции контроллера.

| Ножка | Выводы / функции | Назначение и подключение |
| --- | --- | --- |
| 1 | PD6 / TIM2_CH3, PA1 | A: управление зарядом и разрядом через R; PA1 не используется |
| 2 | VSS | Общий GND измерительной цепи, питания и UART-адаптера / отладчика |
| 3 | PA2 / OSCO | Не используется |
| 4 | VDD | Питание; развязывающий конденсатор между VDD и VSS рядом с МК |
| 5 | PC1 / TIM2_CH1 | B: к узлу R-C; захват фронтов и принудительный разряд |
| 6 | PC2 | Не используется |
| 7 | PC4 | Выбор UART/SWIO при запуске, затем запрос данных по спаду; внутренняя подтяжка вверх |
| 8 | PD5 / UTX, PD1 / SWIO, PD4 | UART TX 9600 8N1 либо SWIO; PD4 не используется |

PD6 и PA1 объединены на ножке 1. 

Режим ножки 8 выбирается один раз при запуске по PC4:

- Если PC4 не подключён или имеет высокий уровень, включается **UART TX** на PD5/UTX, 9600 бод, 8N1.
- Если PC4 замкнут на GND, доступен **SWIO**. UART не включается, GPIO ножки 8 не перенастраиваются.

Для смены режима нужен перезапуск. В режиме UART контроллер должен держать PC4 высоким при запуске, затем формировать отрицательные фронты для запроса данных. Подходит выход с открытым стоком и общий GND.

Во время измерения B работает как плавающий цифровой вход без подтяжек. После измерения оба вывода удерживаются в нуле, B становится выходом. Перед следующим измерением B возвращается во вход.

## Тактирование и измерения

- HSI, номинально 24 МГц, без PLL; делитель HCLK равен 1. Заводская настройка HSI сохраняется.
- TIM2: внутреннее тактирование.
- Один отсчёт при 24 МГц занимает около 41,7 нс; 0,5 мкс соответствует примерно 12 отсчётам.
- Захват CH1 по одному фронту, без фильтра и деления входных событий.

A переключается при `CNT=START_DELAY_TICKS` (по умолчанию 8). Результат содержит эту добавку. Для сравнения изменений её можно не вычитать. Остановка и опрос выполняются программно, но значение фиксируется аппаратно в CH1CVR. Перед каждой фазой явно обнуляется CNT, перед зарядом выполняется сброс TIM2.

Выдержки задаются независимо:

| Макрос в коде | Параметр Make | По умолчанию | Назначение |
| --- | --- | --- | --- |
| `CHARGE_SETTLE_LOOPS` | `CHARGE_LOOPS` | 64 | После захвата заряда, перед разрядом через R |
| `DISCHARGE_SETTLE_LOOPS` | `DISCHARGE_LOOPS` | 0 | После принудительного разряда GPIO, перед следующим измерением |

## Статистика

В одном окне накапливаются **128 сумм разряда** без передачи промежуточных значений:

```text
m = медиана 128 сумм разряда
total = сумма |сумма[i] - m|
D = total / 128
value_milli = round(D * 1000) = (total * 1000 + 64) >> 7
```

`value_milli` хранит значение `D` в тысячных, округлённое к ближайшему целому. Результат выражен в отсчётах таймера **для суммы блока**, не отдельного измерения. Сравнивать значения следует при одинаковом `SAMPLES`.

В `statistics.h` расчёт выполняется с целочисленной арифметикой, данные сортируются вставками.

## Протокол запроса данных

- Автоматической передачи нет. В режиме UART отрицательный фронт PC4 запрашивает все накопленные **готовые результаты**, от самого старого к новому. До заполнения первого окна данных нет.
- Вместимость кольцевого буфера задаёт `BUFFER_CAPACITY` (по умолчанию 32). При заполнении новый результат вытесняет самый старый. Одна запись соответствует полному окну из 128 блоков.
- Каждая запись содержит ровно **6 бинарных байтов**:

| Смещение | Поле |
| --- | --- |
| 0 | `seq`, номер окна (`uint8_t`) |
| 1-4 | `value_milli`, `uint32_t`, big-endian: `[31:24]`, `[23:16]`, `[15:8]`, `[7:0]` |
| 5 | CRC-8 первых пяти байтов |

Номер назначается при завершении окна: `00`, `01`...`FF`, затем снова `00`. Вытеснение и очистка буфера не сбрасывают счётчик; перезапуск микроконтроллера сбрасывает его.

CRC-8/ATM: polynomial `0x07`, init `0x00`.

```text
seq=00, value_milli=125 (D=0.125): 00 00 00 00 7D 74
seq=7F, value_milli=125 (D=0.125): 7F 00 00 00 7D DA
```

Пачка из 32 записей занимает 192 байта: 200 мс при 9600 8N1 без межбайтовых пауз. Во время передачи измерения приостановлены.

## Энергосбережение и отладка

По умолчанию после каждого блока включён Standby. Перед сном A и B удерживаются в нуле, TIM2 остановлен. RAM и состояние периферии сохраняются, выполнение продолжается без сброса; тактирование проверяется и возвращается к HSI 24 МГц.

AWU использует LSI и будит ядро.

При `AWU_WINDOW=29` номинальный сон составляет:

```text
64 * (29 + 1) / 128000 = 15 мс
```

Частота LSI по даташиту составляет 100-150 кГц, поэтому точного секундного расписания нет. 

## Сборка

Нужны bare-metal GNU RISC-V GCC с поддержкой RV32EC / ILP32E и GNU Make. Используется ISA `rv32ec_zicsr_zifencei`, без WCH-специфичных инструкций и interrupt ABI.

```sh
make
make SAMPLES=131
make BUFFER_CAPACITY=128
make CHARGE_LOOPS=1200 DISCHARGE_LOOPS=2400
make STANDBY=0
```

По умолчанию используется префикс `riscv32-none-elf-`. Для другого toolchain:

```sh
make CROSS_COMPILE=riscv-none-elf-
```

Параметры по умолчанию: `SAMPLES=16 CHARGE_LOOPS=64 DISCHARGE_LOOPS=0 STANDBY=1 AWU_WINDOW=29 BUFFER_CAPACITY=32`.

`SAMPLES` допускает значения 1..131. Препроцессор допускает `BUFFER_CAPACITY=1..256`, но фактический предел определяется RAM и линкером: 128 записей помещаются, 256 не помещаются. Каждая запись занимает 5 байт RAM: значение и номер хранятся в отдельных массивах без выравнивания структуры, CRC не хранится. Для 32 записей это 160 байт плюс 8 байт индексов и 1 байт счётчика; возможно дополнительное выравнивание секций. Линкер резервирует не менее 256 байт под стек.

Результаты:

```text
build/<SAMPLES>/<CHARGE_LOOPS>-<DISCHARGE_LOOPS>/sleep-<STANDBY>-<AWU_WINDOW>/buffer-<BUFFER_CAPACITY>/firmware.{elf,bin,hex,map,lst}
```

Разные параметры имеют отдельные каталоги, ручная очистка при их смене не нужна. `.lst` содержит дизассемблирование. Прошивка рассчитана на загрузку из начала пользовательской Flash (адрес 0 в `link.ld`), 16 КБ Flash и 2 КБ RAM, не на запуск через IAP-загрузчик.

## Файлы и проверки

- `main.c`: настройка, измерения, статистические окна, кольцевой буфер и передача по запросу.
- `statistics.h`: расчёт отклонения и преобразование в тысячные.
- `registers.h`: необходимые регистры и маски.
- `startup.S`: стек, gp, копирование `.data` и RAM-кода, очистка `.bss`, вход в `main`; неожиданные исключения уходят в бесконечный цикл.
- `link.ld`: карта памяти и секции.
- `tests/test_statistics.py`, `tests/test_protocol.py`, `tests/test_standby.py`: хост-проверки математики, протокола и управления сном.
- `tests/delay_probe.c`, `tests/discharge_probe.c`: диагностические прошивки.
- `measurements/`: данные и сводки аппаратных испытаний.

Хост-тестам нужны Python 3 и компилятор C (`cc` или `HOST_CC`).

```sh
python3 -m unittest discover -s tests
```

### Зарядная выдержка

Диагностическая прошивка `tests/delay_probe.c` использует измерения и задержки из `main.c`, собирает данные без UART и чтения RAM отладчиком, затем останавливает сбор. Flash проверялась чтением обратно. Датчик неподвижен, разрядная выдержка составляет 2400 итераций.

Проверены отдельные сборки с зарядной выдержкой 2400, 300, 36, 9, 4, 2, 1 и 0. Чтобы исключить влияние компоновки, проведены серии с изменением выдержки внутри одного бинарного файла и повторными контрольными этапами по 2400 итераций. Собирались по 2048, 4096 и 8192 измерения на этап; первые 64 отбрасывались.

| Зарядная выдержка, итерации | Средний захват разряда, такты TIM2, в завершённых сериях одного бинарного файла |
| --- | --- |
| 2400, контроль | 14.921-14.936 |
| 0, 36, 75 | 14.897-14.908 |
| 150 | 14.906-14.918 |
| 300 | 14.910-14.929 |
| 600 | 14.916-14.927 |
| 900 | 14.915 |
| 1200 | 14.922-14.930 |

Индивидуальные захваты разряда составляют 14 или 15 тактов, а захваты заряда составляют 11 или 12. Они включают 8 тактов задержки запуска и задержку захвата, поэтому не равны чистому времени RC-перехода. 

Сборка диагностической серии 600/900/1200 с чередованием контрольных 2400, по 4096 измерений на этап:

```sh
make delay-probe DISCHARGE_LOOPS=2400
```

Путь к бинарному файлу указан в выводе Make; адрес и размер структуры `delay_probe` указаны в соответствующем `probe.map`.

### Принудительный разряд GPIO

В `tests/discharge_probe.c` сравниваются пары: заряд после длинного разряда (не менее 2400 итераций) и после разряда с проверяемой выдержкой. Датчик неподвижен, зарядная выдержка составляет 1200. Между разрядом и проверяемым зарядом нет обновления гистограмм, счётчиков или чтения отладчиком; перевод B во вход записан непосредственно в диагностическом коде.

После 64 прогревочных пар собирались 4096 пар, RAM читалась после остановки сбора.

| Разрядная выдержка | Средний заряд после длинного разряда | После проверяемого разряда | Разность, такты |
| --- | --- | --- | --- |
| 2400 | 11.004395 | 11.003662 | -0.000732 |
| 0, запуск 1 | 11.003906 | 11.003662 | -0.000244 |
| 16 | 11.003174 | 11.002197 | -0.000977 |
| 0, запуск 2 | 11.003174 | 11.003418 | +0.000244 |


```sh
make discharge-probe CHARGE_LOOPS=1200 DISCHARGE_LOOPS=0
```
